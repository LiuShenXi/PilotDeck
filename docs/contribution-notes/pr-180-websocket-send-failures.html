PilotDeck PR #180 技术复盘：WebSocket 发送失败的 UI 可见化

这份文档用于复盘一次真实开源贡献：从本地排障中发现 PilotDeck 聊天界面在 WebSocket 未连接时只写 console，不给用户明确反馈， 到通过最小改动修复状态机误导，并提交 PR。

项目：OpenBMB/PilotDeck PR：#180 分支：fix/websocket-send-failed-feedback 提交：088fb24 日期：2026-06-08

一句话总结

当 PilotDeck WebSocket 尚未连接或已经断开时，用户点击发送后，旧实现只在控制台打印 WebSocket not connected，聊天 UI 却可能进入乐观的 Processing / Sending 状态。 PR #180 让底层发送函数返回发送结果，并让 composer 在发送失败时保留输入、停止 loading、显示可见错误消息。

背景与问题现象

这个问题来自本地调试 PilotDeck 模型调用链路时的实际体验。用户在聊天输入框发送消息后，界面可能显示正在发送或正在处理， 但中转服务没有收到任何模型请求。继续往下查后发现，问题并不总是 provider key、base URL 或模型名错误； 有时是浏览器到 UI server 的 WebSocket 链路本身没有建立成功。

用户看到的现象

  • 点击发送后，输入框清空。
  • 聊天界面出现乐观用户消息或 Processing 状态。
  • 服务端 / 中转平台看不到模型请求。
  • 浏览器控制台可能只有 WebSocket not connected。

问题的产品影响

这是典型的“状态反馈误导”：用户以为请求已经发出，实际上消息连本地 WebSocket 都没有成功发送。 这种问题会把排障方向带偏，让用户误查 API key、模型配置、路由、网关、代理等更复杂的部分。

关键代码链路

这次修复涉及的是 UI 发送链路，不是模型 provider 调用链路。

1. 用户提交 useChatComposerState 处理输入框提交。
2. 构造命令 startSessionCommand 组装 pilotdeck-command。
3. WebSocket 发送 WebSocketContext.sendMessage 调用浏览器 socket.send()。
4. 旧行为 未连接时只 console.warn，调用方不知道失败。
5. 新行为 返回 false，composer 显示错误并保留输入。

旧实现的核心问题

const sendMessage = useCallback((message: any) => {
  const socket = wsRef.current;
  if (socket && socket.readyState === WebSocket.OPEN) {
    socket.send(JSON.stringify(message));
  } else {
    console.warn('WebSocket not connected');
  }
}, []);

这段代码的问题不是没有检测 WebSocket 状态，而是检测结果没有进入业务状态机。 对调用方来说，sendMessage 的返回值永远是 undefined， 因此 composer 会继续执行乐观 UI 更新：添加用户消息、设置 loading、清空输入框。

根因分析

层级 发现 结论
模型 / provider 中转平台没有请求记录。 请求没有到达模型层。
UI WebSocket 发送函数在未连接时只打印 warning。 失败发生在浏览器到本地 UI server 的发送阶段。
Composer 状态机 发送前后没有检查发送结果，直接进入乐观状态。 UI 状态和真实发送状态脱节。
面试时可以强调：这个 bug 的本质不是“WebSocket 会断开”，而是“发送失败没有被建模为业务结果”。 因此修复点不是简单加一个 toast，而是让底层 API 显式返回发送成败，再让上层状态机基于结果分支处理。

修复设计

目标

  • WebSocket 未连接时，用户能在聊天区域看到明确错误。
  • 发送失败时不要清空输入，方便用户等待重连后重试。
  • 发送失败时不要进入 Processing / Sending 状态。
  • 保持改动范围小，不引入全局 toast 系统或大规模状态重构。

为什么选择返回布尔值

直接让 sendMessage 返回 true / false 是最小、最可测试的改法。 它不改变 WebSocket 的连接生命周期，也不要求所有调用方立即处理失败。旧调用方可以继续忽略返回值； chat composer 作为用户发送入口，则可以选择处理失败并展示 UI。 

const sendMessage = useCallback((message: any) => {
  const socket = wsRef.current;
  if (socket && socket.readyState === WebSocket.OPEN) {
    try {
      socket.send(JSON.stringify(message));
      return true;
    } catch (error) {
      console.error('WebSocket send failed:', error);
      return false;
    }
  }
  console.warn('WebSocket not connected');
  return false;
}, []);

具体改动

文件 改动 作用
ui/src/contexts/WebSocketContext.tsx sendMessage 从 void 改为 boolean。 把底层 WebSocket 发送成败显式暴露出来。
ui/src/components/chat/utils/sessionLauncher.ts startSessionCommand 返回 { sessionId, sent }。 保留原来的 session id 语义，同时把发送结果传回 composer。
ui/src/components/chat/hooks/useChatComposerState.ts 发送失败时清理 pending 状态、停止 loading、追加错误消息、保留输入。 避免 UI 误导用户请求已经进入处理流程。
sessionLauncher.test.ts 和 useChatComposerState.test.ts 新增发送成功/失败和错误提示文本测试。 保证以后不会退回“只写 console”的行为。

TDD 修复过程

  1. 先写 sessionLauncher.test.ts，要求 startSessionCommand 在 sendMessage 返回 false 时返回 { sent: false }。
  2. 跑测试，旧实现失败：实际返回的是字符串 "new-session-test"， 说明测试确实覆盖了旧行为。
  3. 修改 sendMessage 和 startSessionCommand 的返回值模型，让测试变绿。
  4. 再补 composer helper 测试，要求失败消息是 error 类型并包含 not connected 和 try again。
  5. 最后把 composer submit 流程改成：先尝试发送，失败则显示错误并 return，成功才进入乐观状态。
面试可讲点：这不是“写完再补测试”，而是先让旧行为失败，再用最小实现让测试通过。 这个过程能证明测试确实抓住了问题，而不是只覆盖新代码。

技术取舍

为什么不直接加 toast？

因为 toast 只能解决“看见提示”的表象，不能解决 composer 状态机已经清空输入、进入 loading 的问题。 本次修复先把发送成败建模出来，再在 composer 中控制状态流，属于更靠近根因的修复。

为什么不让所有调用方都处理失败？

PilotDeck 中 sendMessage 还用于 presence、abort、permission 等场景。 让所有调用方一次性改为强制处理会扩大 PR 范围。当前 PR 只处理用户最敏感的聊天提交路径； 其他调用方忽略返回值时行为和过去一致。

为什么失败时保留输入？

WebSocket 断开通常是临时状态。保留输入能让用户在连接恢复后直接重试，避免用户重新组织问题。 同时不进入 Processing 可以避免用户误以为模型已经开始处理。

面试高频问答准备

Q：这个 bug 的根因是什么？ A：WebSocket 未连接时，底层 sendMessage 只打印 warning，没有把失败结果返回给调用方。 composer 在不知道发送失败的情况下继续执行乐观 UI 更新，导致输入清空、loading 开启，但请求其实没有发出去。
Q：你为什么选择改返回值，而不是直接在 WebSocketContext 里弹提示？ A：因为 WebSocketContext 是底层通信层，它不知道当前消息对应哪个 UI 场景。把结果返回给 composer， 可以让真正拥有上下文的地方决定是否保留输入、停止 loading、显示错误消息，职责更清晰。
Q：这个改动会不会破坏其他调用方？ A：兼容性风险较低。JS/TS 里调用方可以忽略返回值；同时 startSessionCommand 支持旧式 void sendMessage，只有明确返回 false 才视为失败。 也就是说旧调用方行为基本保持不变，chat submit 路径获得了额外的失败处理。
Q：为什么发送失败时不添加用户消息？ A：因为消息没有发到后端，添加用户消息会制造“已经提交”的错觉。更合理的行为是保留输入和草稿， 显示连接错误，让用户等重连后重试。
Q：你怎么验证不是 provider 或模型配置问题？ A：当中转平台没有任何请求记录时，说明请求没有到 provider 层。进一步看浏览器控制台和 UI WebSocket 状态， 发现发送函数在 socket 未连接时只 warning。由此定位到 UI WebSocket 发送阶段，而不是模型配置阶段。
Q：这次贡献有什么工程价值？ A：它改善了失败可观测性和用户反馈，减少排障误导；同时把通信层失败显式建模为返回值， 让上层状态机能做正确分支处理。这比单纯补一个提示更稳。

复盘与后续扩展

这次 PR 聚焦最小修复，没有做全局离线状态管理。后续如果继续贡献，可以考虑：

  • 在 app shell 层显示全局 WebSocket 连接状态。
  • 给 abort / permission / presence 等调用方逐步增加失败处理。
  • 把连接恢复后的重试体验做得更顺滑，例如提供“重新发送”按钮。

但这些都属于下一阶段功能，不适合塞进本次 bugfix PR。小而清晰的 PR 更容易被维护者 review 和合并。
